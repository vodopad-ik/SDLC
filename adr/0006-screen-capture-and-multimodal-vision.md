# ADR 0006 — Захват экрана и мультимодальный анализ задач (Vision)

- **Статус**: принято (2026-10-25)

## Контекст
На технических собеседованиях и рабочих звонках задания часто не зачитываются вслух, а демонстрируются
на экране: условие задачи (LeetCode / Codeforces), кусок кода в IDE, диаграмма системного дизайна,
слайд или стек-трейс ошибки.
Ассистент должен по горячей клавише мгновенно «увидеть» экран, распознать задачу и выдать готовое
решение / подсказку.

Ключевое требование: окно оверлея Elor может находиться прямо поверх экрана (например, перекрывать
часть браузера с задачей). Захват экрана обязан **полностью игнорировать собственное окно**,
чтобы оно не закрывало текст задачи и не загрязняло контекст нейросети.

## Решение
1. **Исключение собственного окна из захвата**:
   Все окна Elor (`OverlayWindow`, диалоги) создаются с системным атрибутом
   `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` (ADR 0001).
   При вызове системных API захвата экрана (`BitBlt` с Desktop DC, DXGI Duplication или Windows.Graphics.Capture)
   DWM-композитор Windows 11 **автоматически исключает окно Elor из кадра**, отрисовывая пиксели,
   находящиеся под ним. Окно Elor остаётся видно пользователю, но на захваченном скриншоте отсутствует.
   Не требуется прятать или мигать окном во время скриншота.

2. **Захват и предобработка изображения**:
   - Новый модуль `elor_vision` (Win32 GDI / BitBlt с виртуального рабочего стола или активного окна `GetForegroundWindow`).
   - Полученный растровый буфер при необходимости масштабируется (макс. ширина/высота 1920 px для экономии токенов и ускорения передачи)
     и кодируется в JPEG в памяти (качество 85, размер ~150–350 КБ). Задержка захвата и сжатия ≤ 25 мс.

3. **Мультимодальная генерация (Gemini Vision)**:
   - Изображение передаётся в `ILlmProvider::generate` как часть запроса (`image/jpeg` inline data).
   - Gemini Flash (`gemini-2.5-flash` / `gemini-3.8-flash`) параллельно получает системный промт
     специализации решения задач («Выдели условие задачи на изображении, дай оптимальный алгоритм,
     асимптотику O(...) и чистый код с разбором краевых случаев») с учётом языка программирования и контекста сессии.
   - Ответ стримится через SSE потоком токенов.

4. **Инвариант «никогда не затирать» (ADR 0005)**:
   - Решение задачи оформляется как карточка нового типа `vision_solution`.
   - Она добавляется в общую ленту карточек (append-only), не затирая голосовую транскрипцию
     и ответы на реплики собеседника.

5. **Управление**:
   - Глобальный хоткей по умолчанию: `Ctrl+Alt+S` (Scan screen & solve).
   - Команда локального API: `vision.scanScreen` `{ "target": "fullscreen" | "active_window", "customPrompt"?: "..." }`.

## Последствия
- Возможность проходить лайв-кодинг и секции архитектуры с графическими материалами без перепечатывания условий.
- Задержка «нажатие хоткея → первые слова решения на экране»: ~600–900 мс (быстрее, чем прочесть задачу человеку).
- Чистая реализация на Win32 без сторонних тяжёлых библиотек (GDI / GDI+ / stb_image_write).
- Расширение протокола API v1 новым типом карточки `vision_solution`.
